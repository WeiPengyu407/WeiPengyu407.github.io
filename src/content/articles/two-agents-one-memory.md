我这台机器上跑着两个 AI 编程 agent：一个是 Cursor 里的，一个是命令行的 Kimi Code。它们共用一个 Obsidian vault 当长期记忆——偏好、项目状态、踩过的坑，都写在里面。

协议很简单：

- 两个信箱，`[[给Kimi]]` 和 `[[给Cursor]]`
- 派活往对方信箱追加一条，标 `[open]`
- 收活的一方干完，往自己这边的信箱写回执，再把原条目标成 `[done]`
- 开干之前先读一遍自己的信箱

搭起来花了不到一小时。之后所有的问题，全都出在「确认」这一步上。

## 失效一：读到空，退出码 0

Obsidian 的官方 CLI 在没有伪终端的时候会返回空字符串，而退出码是 0。这个坑我单独写过一篇。

放在这套协作机制里，它的后果要严重得多：**agent 读信箱读到空，会如实汇报「信箱里没有新任务」。**

它没说谎。它拿到的就是空的。于是派活的一方以为交接完成了，收活的一方以为没活，两边都没有任何报错。

后来在 Cursor 侧的笔记里翻到一句自记：那段时间它「所有非交互读取都是静默空结果」。也就是说有一整段时间，每一次交接都丢了，而两边的日志都是干净的。

## 失效二：写入返回成功，但立刻读不回来

这一条是我在准备这篇文章的时候现场撞上的。

我让 Kimi 去核对一批事实，要求它把结论写进 `[[给Cursor]]` 信箱。它照做了：调 CLI 追加，退出码 0。然后它做了件对的事——回读验证。结果 grep 不到刚写的内容。

于是它判定写入失败了，改成直接往文件里追加。

然后 CLI 那次写入延迟落盘了。同一份一万多字的内容进去了两遍。

它靠字节数发现了重复（文件 21780 字节，原文 522，内容块 10629，正好两份），自己去重、验证，然后在回复里主动交代了这件事。

这个失效模式比第一条更阴：**回读验证这个动作本身是对的，但「立刻回读」和「返回成功」之间存在竞态**。验证失败于是重试，重试造成重复——重试是所有健壮性写法里最标准的一条，在这里恰好是错的。

正确的写法是让追加操作幂等（比如带一个内容指纹，写之前先查在不在），或者容忍延迟再读一次，而不是从一次读不到直接跳到「失败了，重来」。

## 失效三：纯轮询，没有推送

没有任何守护进程在盯着信箱。

「开干前先读信箱」是写在两边的规则里的，但它只是一条规则，执行与否取决于那次会话有没有想起这件事。派活的一方如果不额外口头提醒一句，收活的一方可能永远不知道有新条目躺在那儿。

这是这套机制目前最大的结构性弱点，而且它不是 bug，是设计上就缺一环。

## 失效四：三份记录，三种说法

有一份工作（一个监听空闲事件的守护进程），在三个地方留下了记录：一边的信箱回执写是 A 做的，另一边的回执写是 B 做的，第三份工作笔记里又是另一种口径。

没有一处是有意写错的。每个 agent 都在如实记录自己视角里发生的事，而它们的视角本来就不重叠。共享一份记忆并不会自动带来一致的记忆。

## 最狠的一条：agent 审计不了自己的过去

我问 Kimi：你当初判定那个任务「完成」的依据是什么？验证了哪一步、没验证哪一步？

它的回答是：**不确定，无记录。**

它没有保留任何历史会话。它能给我的全部证据是文件的 mtime、日志、autostart 条目的内容、vault 里的笔记往来——也就是说，它是像考古一样反推自己两天前做过什么的，而且它明确把哪些是记录、哪些是推断分开标了。

这件事让我改了心里的一个模型。我原来以为 agent 交付的东西不可靠，问题在它的能力。现在我觉得更根本的问题是**它无法回答「我当时为什么认为这是对的」**。没有这个，你没法从一次失败里学到任何可迁移的东西，只能重新验一遍。

## 现在协议里加了什么

四条，都是从上面那些失效里长出来的：

**成功的读取不许返回空**。任何一次读操作，退出码 0 但内容为空，一律当异常往上抛，不许当成「那里确实没东西」。这一条单独就挡掉了失效一整类。

**写完要回读，但不许从一次读不到就判定失败**。要么让写操作幂等，要么留出延迟再读。

**派活的时候顺手提一句**。在推送机制补上之前，这是唯一能保证信箱被读到的办法。承认它土，比假装规则会自动执行好。

**要求标注置信度**。给 agent 的提示词里必须写「拿不准就说不确定，不要猜」。

最后这条的效果差别大得出乎我意料。不加这句，它给出的是流畅、完整、看着很可信的答案——而编造的答案和实测的答案长得一模一样，我分辨不出来。加上这句之后，它这次交回来的每一条都带着「确定 / 大概 / 不确定」的标注，还主动写了一段取证边界声明，说明哪些结论来自文件证据、哪些来自推断。

一句话换来的可用性提升，比我给它换个更强的模型明显。

## 共同点

回头看，这四类失效是同一件事的不同穿法：**操作返回成功，实际什么也没发生，而且没有任何一方有理由怀疑。**

人在这种情况下会起疑——「怎么会一条都没有」。agent 不会，它会把空结果当成事实，然后基于这个事实继续往下推。它的诚实反而让错误传得更远。

所以真正需要设计的不是共享，共享是最简单的部分。需要设计的是**每一次交接都必须有一个会失败的断言**。没有断言的交接，等于没有交接——只是两边都以为有。
