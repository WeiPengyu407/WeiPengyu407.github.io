我在自己站上写了这么一句：

```markdown
**KWin 对 `ext-*` 系列不是一概不实现，是挑着实现。**空闲通知它要，会话锁它不要。
```

页面上出来的是这样：

```
**KWin 对 ext-* 系列不是一概不实现，是挑着实现。**空闲通知它要，会话锁它不要。
```

星号原样显示，加粗没生效。构建成功，零警告。

同一篇文章里另外三处加粗全都正常。所以这不是「渲染器不支持加粗」，是这一处有什么东西不一样。

## 先排除掉一个错误猜测

我的第一反应是中文全角标点的问题——闭合星号紧挨着一个 `。`，多半是渲染器把全角字符归类归错了。

这个猜测很自然，而且是错的。把全角句号换成半角句点，一样失效：

```markdown
**like this.**next
```

英文、半角、纯 ASCII，照样渲染成字面星号。所以跟中文无关。

## 实测边界

我把闭合星号前后的字符类型排列组合，全跑了一遍。用的是我自己站上的 Markdown 引擎，然后用 CommonMark 的参考实现交叉验证，两边结果完全一致：

| 写法 | 结果 |
| --- | --- |
| `**这样写**。下一句。` | 成功 |
| `**这样写。**下一句。` | **失效** |
| `**这样写。**。下一句。` | 成功 |
| `**这样写。**` （行尾结束） | 成功 |
| `**这样写。** 下一句。` （加空格） | 成功 |
| `**这样写**下一句。` | 成功 |
| `**like this.**next` | **失效** |

只有一种组合会失效：**闭合星号前面紧邻标点，后面紧跟一个既不是空白也不是标点的字符**。

前面不是标点就没事，后面是标点或空白也没事。必须两个条件同时满足才炸。

## 规范里就是这么定的

这不是哪个渲染器的 bug。CommonMark 规定，`**` 只有构成「右侧贴合」（right-flanking）时才能用来闭合强调。而右侧贴合的定义是：

1. 前面不是空白，并且
2. 前面不是标点，**或者** 前面是标点且后面是空白或标点。

代入 `实现。**空`：前面是 `。`，是标点，第一个分支不成立；后面是 `空`，既不是空白也不是标点，第二个分支也不成立。于是这个 `**` 不构成右侧贴合，没有闭合资格。

闭合方没了，开头那个 `**` 也就配不上对，两串星号一起退化成普通字符。这解释了为什么错误现象是「一对星号都露出来」，而不是「只少了后半个」。

## 开头的星号有一条对称的规则

写这篇的时候我又撞了一次，这回是在另一头。这句渲染失败：

```markdown
这件事的教训不是「tkinter 不能做锁屏」，是**「看起来生效」和「生效」之间差的是一个想绕过它的人**。
```

闭合那边完全合法（前面是 `人`，不是标点）。问题出在开头：`是**「` —— 开启星号前面是汉字，后面紧跟一个中文引号。

「左侧贴合」的定义和右侧完全镜像：后面不是空白，并且，后面不是标点、**或者**后面是标点且前面是空白或标点。这里后面是 `「`（标点），前面是 `是`（文字），两个分支都不成立，于是它没有开启资格。

实测确认：

| 写法 | 结果 |
| --- | --- |
| `是**「引号开头」的加粗**。` | **失效** |
| `：**「引号开头」的加粗**。` | 成功 |
| 行首 `**「引号开头」的加粗**。` | 成功 |
| `是**普通开头的加粗**。` | 成功 |

所以完整的记法是：**加粗的两端都不要贴着中文标点**——里面第一个字和最后一个字都是普通文字最稳。而中文写作里，一句话被引号或书名号开头是很常见的写法，所以这一头也不算罕见。

## 为什么英文作者碰不到

因为这套规则靠「前后字符是空白、标点还是文字」来猜作者的意图，而这个猜法默认词与词之间有空格。

英文里句号后面天然跟一个空格，正好命中「前面是标点且后面是空白」这个豁免分支。中文标点后面不加空格，于是每一个「`。`+ 闭合星号 + 下一句」都精准落在唯一失效的那个格子里。

规则本身没写错，它只是为分词靠空格的文字设计的。中文不满足这个前提。

## 修法

把句末标点挪到加粗外面：

```markdown
**KWin 对 `ext-*` 系列不是一概不实现，是挑着实现**。空闲通知它要，会话锁它不要。
```

读起来完全一样，渲染就对了。规律好记：**中文里句末的标点永远放在加粗的外面**。

## 让构建替你盯着

这个坑真正麻烦的地方不是修，是发现。

它没有报错，没有警告，退出码是 0。页面能打开，排版没乱，只是句子中间多了四个星号——而你写这篇文章的时候已经把它读过五遍了，眼睛早就滑过去了。

所以我不靠自己记得检查，让构建来失败：

```js
// 构建后扫产物 HTML，正文里出现字面 ** 就退出码 1。
// 先剥掉 <pre> 和 <code>，代码块里的 ** 是合法内容。
const prose = html
  .replace(/<pre[\s\S]*?<\/pre>/g, "")
  .replace(/<code[\s\S]*?<\/code>/g, "");

for (const m of prose.matchAll(/\*\*[^*\n]{0,30}/g)) {
  problems.push(`${file}: ${m[0].trim()}`);
}
```

挂在 `npm run build` 后面，一共二十行。

我倾向于认为这类检查比修好具体某一处更值钱。**「合法输入 + 静默降级」是最贵的一类失败**：没有任何一环报错，所以没有任何一环会拦住你，错误一路走到读者眼前。这种失败模式不能靠注意力防，只能靠一条会失败的断言防。
