我想把 Windows 那种图片密码搬到 Linux 上：锁屏显示一张照片，在约定的位置连点三下就进桌面，不打字。

我让一个 AI agent 做了。开机试，能用——照片出来，点三下，进桌面。

用了两天，发现一个规律：**它只在开机后的第一次生效**。之后只要屏幕自然熄掉再亮，出来的就是原本那个文字密码框。

于是我的问题变成了「为什么息屏之后它不触发」。这个问题问错了。

## 症状描述把我带偏了

「只在开机时生效」这句话里藏了一个前提：有一个东西在开机时正常工作，在息屏后失效了。顺着这个前提往下想，要查的自然是触发时机——是不是缺了个空闲事件的监听，是不是唤醒的时候没重新拉起来。

我在这个方向上查了不少东西。都不是。

真相是它**从来没有生效过**。开机那次也没有。

## 它是什么

那一版的实现是一个 Python tkinter 窗口：全屏、置顶、显示图片、在配置好的相对坐标附近连点三下就把自己销毁掉。窗口销毁就算「解锁」。Esc 和关闭按钮都屏蔽了。

这里没有任何一个环节在锁定这台机器。它是一张贴在屏幕最上层的图片。

Wayland 下普通客户端拿不到输入独占——那是 `ext-session-lock-v1` 这类会话锁协议才有的能力，而 tkinter 窗口只是个普通窗口。所以 Alt+Tab 能切走，Ctrl+Alt+F2 能切到 TTY，从另一台机器 `ssh` 进来 `kill` 掉那个进程，桌面就露出来了。

## 那为什么开机看起来是对的

因为开机本来就没有密码环节。

配套改动里有一个 `sddm-autologin.conf`，把 SDDM 配成了自动登录。也就是说开机根本不问密码，直接进桌面，然后自启项把那个 tkinter 窗口弹出来。

它不是替换了开机密码，它是**盖住了一个已经被删掉的密码环节**。屏幕上没有别的东西跟它抢，所以它看起来在工作。

而息屏之后接手的是 `kscreenlocker`，那是 KDE 真正的锁屏，它弹的是系统密码框。图片锁从来没有挂进这条链路。所谓「变回文字密码」不是退化，那是这台机器唯一一处真的在锁的地方。

两个现象，一个原因：这东西没有参与过任何一次真实的锁定。

## 验一个锁屏是不是真的在锁

三条，任何一条能进桌面，它就不是锁屏：

```bash
# 1. 锁屏状态下按 Alt+Tab，看能不能切到别的窗口

# 2. 锁屏状态下按 Ctrl+Alt+F2 切到 TTY，登录，然后：
loginctl list-sessions      # 看会话状态是不是 locked

# 3. 从另一台机器进来，杀掉那个「锁屏」进程
ssh 这台机器 'pkill -f 你的锁屏程序'
# 桌面露出来了 → 它只是个窗口
```

第三条最狠，也最能说明问题：真正的锁屏被杀掉之后，合成器要么重新拉起 greeter，要么直接停在黑屏，不会把你的桌面交出来。一个杀掉就消失的锁屏，等于一个写在便签上的密码。

## 后来怎么做的

不自己写锁屏程序。KWin 没有实现 `ext-session-lock-v1`（这件事我单独写了一篇），所以在 Plasma 上你没有「换一个锁屏程序」这个选项，只有「改造 kscreenlocker」这个选项。

最后的做法是把图片密码写成 kscreenlocker 的 greeter QML，跑在系统锁屏进程里面。输入独占是 greeter 自带的，我不需要去争。点够次数之后，把预存的密码交给 PAM，走的是和输密码完全相同的那条认证路径。

同时把 KDE 的 `Autolock` 恢复成 `true`。中间还有一版方案是关掉系统自动锁、用一个守护进程监听空闲事件来弹图片锁，也被我推翻了——那个方案的失败模式是：守护进程一挂，机器就完全不锁了，而且不会有任何提示。用一个「坏了就静默地什么都不做」的东西去替换一个能工作的系统功能，是把风险换了个方向放大。

## 教训

这件事的教训不是 tkinter 不能做锁屏。

**「看起来生效」和「生效」之间，差的是一个想绕过它的人。**

安全性质的东西，验收必须是对抗性的：不是确认它在你配合的时候能工作，而是确认它在你主动破坏的时候仍然拦得住。我最初的验收是「弹出来了、点三下进去了」，这个测试里我全程在配合它。

顺便，这也是把活派给 agent 时最容易漏掉的一件事。agent 会验证它实现的那条路径通不通，不会替你去想有没有别的路可以绕过去——除非你在派活的时候就把「绕过去的方法」写成验收标准。
