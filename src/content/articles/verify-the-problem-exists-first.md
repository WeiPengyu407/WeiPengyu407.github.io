我的语音输入准确率掉得很明显。查下来是麦克风增益开得太满，录到的每一段都在 0 dBFS 削顶，成千上万个采样被切平了。降下来就好了：

```bash
wpctl set-volume @DEFAULT_AUDIO_SOURCE@ 0.18
```

然后我给自己记了一条待办：**这个设置重启会掉回去，得做持久化**。

方案我当时就想好了：写一个 systemd user unit，`After=pipewire.service`，开机跑一次 `wpctl set-volume`。二十行以内，稳，能跑。

## 先验一步

真正动手之前我去看了一眼现在的状态：

```bash
$ wpctl get-volume @DEFAULT_AUDIO_SOURCE@
Volume: 0.18

$ ls ~/.config/wireplumber/
ls: 无法访问: 没有那个文件或目录
```

值还在，但没有任何配置文件。说明维持这个值的东西不是我写的配置。那是谁？

```bash
$ cat ~/.local/state/wireplumber/default-routes
alsa_card.pci-0000_00_1f.3:input:analog-input-internal-mic={
  "channelVolumes":[0.005831, 0.005831], "mute":false, ... }
```

0.005831。而 0.18³ = 0.005832。

`wpctl` 显示的是立方刻度（人耳感知），存下来的是线性值，同一个数。**WirePlumber 自己已经把这个值持久化了**，`default-routes` 就是它开机恢复设备音量用的状态文件。

我要写的那个 service，功能是把一个操作系统已经在做的事再做一遍。

## 验证，而不是相信

这个证据已经很强了，但我这段时间被静默失败坑得有点多——文件里的数字对不等于机制真的生效。所以实测：

```bash
$ wpctl get-volume @DEFAULT_AUDIO_SOURCE@
Volume: 0.18
$ systemctl --user restart wireplumber
$ wpctl get-volume @DEFAULT_AUDIO_SOURCE@
Volume: 0.18
```

进程整个重启，值自己回来了。

于是这条待办不是「完成」，是**删除**。最后的产出是零行代码。

## 我错在哪一步

不是错在方案上，那个 systemd unit 写出来是能用的。错在更早：我把「重启会掉」当成了已知事实，而它其实是个我从没验过的假设。

这个假设怎么来的？因为 `wpctl` 是个命令行工具，命令行工具改的东西通常是进程内状态、重启就没了。这个经验在很多场合是对的，所以它没触发我的怀疑。

**代价最大的假设，都是那种在别的场合确实成立的假设**。完全没道理的猜测活不过五秒钟，一般化过度的经验能一路活到你交付。

还有一个更具体的坏信号，我事后才认出来：**我能在没有测量过问题之前就描述出完整的解法**。这种流畅感很容易被当成经验丰富，实际上它说明我在解决一个记忆里的问题，不是眼前这个。

## 这条能省多少事

我回头翻了翻同一段时间里其他几个决定，规律很一致——事情做小，几乎都发生在「删掉一个需求」而不是「找到一个优雅解法」的时候：

- 想给锁屏做一整套自定义 shell 包，最后是影子掉系统包、只换 `lockscreen` 一个目录，其余全部软链回去。少写的那些代码里本来会长出维护成本，因为系统更新会流过软链，不会流过我的副本。
- 文章列表页原来有滚动淡入，我调了两轮觉得还是别扭。最后是删掉它——那一页的任务是让人快速扫，动效在这里不携带任何信息，只让人对着空白等一拍。
- 加粗静默失效需要一个检查，我没写 remark 插件去解析 AST，而是构建完之后正则扫一遍产物 HTML。二十行。它抓的是「最终页面上有没有露出星号」，比在中间环节判断更接近我真正关心的事。

这几条的共同点不是「写得聪明」，是**先问了一句「这件事需要存在吗」**。

## 落到流程上

我现在把这一步固定下来了：待办上任何一条「修 X」，动手前先跑一条命令确认 X 现在的状态。

只要一条就够，成本是十几秒。它偶尔会让我删掉一整条待办，而这是整个流程里性价比最高的一种产出。

这条对 AI agent 尤其要紧。agent 拿到「修 X」会直接开始修 X——它对任务描述的信任度比人高得多，你说有问题它就认为有问题，然后交付一个能跑的、多余的东西给你。它不会替你怀疑前提，所以前提必须在派活之前就验掉。
